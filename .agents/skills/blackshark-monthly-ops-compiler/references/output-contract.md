# 成果与版本 v0.3

对运营交付两样：月度方案与推进表。保留旧七段式标题和主要分工；模板版本独立于门店当月方案版本。

## 方案模板 0.2

沿 `04_templates/月度运营方案模板.md` 的七段式：本月要做到什么；谁负责什么；本月排期；各板块怎么落地；本月先不做什么；还有哪些要拍板；这套文件怎么用。

开头写门店、月份、文档版本、使用的模板版本、方向状态与简要重点。已定与建议分清；数值不充分时明确不确定性。第四段按经营主项目叙述目的、做法、资源与门店配合，映射推进表的项目编号。第七段保留入口并放真实内嵌视图；本地稿放相对预览链接并注明飞书内嵌未实施。

方向、预算取舍等实质变化回方案，日常状态回表；不能把“文档管方向”理解为冻结后永远不改方向。历史方案保留版本，更新原项目，不另起重复表。

## 推进表模板 0.2

一张业务表、六个状态、五个默认视图。保留原十字段：动作、执行线、状态、归属、交付物/验收、实际情况记录、截止日期、开始日期、承接人、阻塞/待确认。增加两个支撑字段：

- 任务编号：文本，店／月项目内稳定且唯一，重命名动作不变。
- 父任务：关联本表，空表示主项目，子任务指向唯一上级。字段不是最终展开呈现，发布时另外配置和检查原生父子记录显示。

对外视图可隐藏技术编号，不让运营手动维护 ID。原表有其他字段则保留并映射；不得为凑12列删除已使用字段。新增字段是本版模板变化，旧表升级须处理既有记录与显示方式。

树形语义：主项目表达目的及范围，子任务表达可验收工作；确有独立层级可再分解，不为美观制造空父项。执行线用于分类，可跨产品、平台、内容等线；同一主项目下可以有多个执行线。任务数量由工作决定。各子任务可以独立负责；主项目有推进责任，但父项目不能只因文件生成或部分子项完成就标成已完成。

## 机器记录与本地检查

AI 在个人项目保存 `推进表记录.json`，结构：

```json
{
  "store": "示例店",
  "month": "2030-04",
  "plan_revision": "工作稿1",
  "records": [
    {"id":"P1","parent_id":null,"kind":"project","title":"晚餐选择更清楚","line":"经营统筹","status":"进行中","owner":"推进角色","affiliation":"黑鲨","start":"2030-04-01","due":"2030-04-30","acceptance":"项目观察与下一步结论","actual":"","blocker":"","dependencies":[]},
    {"id":"T1","parent_id":"P1","kind":"task","title":"核对套餐入口","line":"平台承接","status":"未开始","owner":"平台角色","affiliation":"示例店","start":"2030-04-01","due":"2030-04-02","acceptance":"页面和可售套餐一致","actual":"","blocker":"","dependencies":[]}
  ]
}
```

代码不做经营判断，仅检查结构并导出：

`python3 scripts/compile_monthly.py --input <记录.json> --out <本次新输出目录>`

正式可执行任务检查增加 `--final`。工作稿缺少责任或日期以 warning 返回；未定任务状态必须解释待定内容。正式检查跳过明确取消及待拍板项，待拍板须注明卡点；其余子任务缺责任、期限或验收不通过。任务可晚于当月结束，以实际跨月依赖为准。

生成：`运营推进表.csv`、`运营推进表结构.json`、`推进表预览.md`、`本地结构检查.json`。原始 JSON 是稳定编号、层级与依赖的本地来源；CSV 是迁移辅助，直接导入不能生成真实人员、父关系或原生树形。需要显示完整原始依赖时在对应记录的阻塞说明中保留依赖，不把未到期前置误记成异常。

检查覆盖编号唯一、父项存在、父子无环、依赖无环、日期有效、状态合法、完成状态不矛盾等；本地通过不等于原生展开、内嵌或业务效果通过。发布回执存个人项目，运营不必阅读技术记录。

## 同一任务后续修改

用任务编号匹配记录，保留真实记录 ID 映射。老表无编号时先以已确认的动作与上下文匹配；歧义列出处理，不猜。修改动作标题不新建任务；只更新受影响字段，不重置执行人填入的状态、实际情况或证据。取消以状态保留，不删除历史。子任务先后与归属调整留原因。
