# 结果回收与交接

## 从诊断接到行动

一项推荐接清：当前问题与依据→本期要改变什么→为什么该做法可能起作用→当前关键产出→谁接收及如何使用→看什么反馈→何时维持、调整或停止。

沿用现有任务 ID、负责人、已完成/取消状态和预算，不把诊断自动转成新增派单。资料收集和建议可在授权内完成；新增投入、对外承诺、发送及发布分别按用户本次及已有授权执行。

| 验收层 | 要回答的问题 | 不能越级宣称 |
| --- | --- | --- |
| 产出 | 内容/产品/工具是否准确、完整、可用，满足关键限制 | 有文件不代表已被使用 |
| 使用 | 接收者是否真接到、上线/执行/交付，在哪些条件下 | 已使用不代表顾客受影响 |
| 顾客行为 | 理解、咨询、购买、核销、到店、选择或复来是否改变 | 同期变化不自动归因该动作 |
| 经营结果 | 在相称窗口与基线下，有无贡献、成本或产能变化 | 收入增长不自动代表利润或净增量 |

经营指标留基线、目标/最低可接受条件、分母、窗口、来源、干扰因素、停止条件及权限。条件未定时给建议及理由，不编成已确认数值。现场无法执行的验收不能写成已达标。

## 结果回来先分情况

| 结果类型 | 如何改判 |
| --- | --- |
| 没执行、没交付或没有记录 | 查交接/执行或记录，不否定顾客需求 |
| 执行但关键条件没兑现 | 改产出或门店承接；需求主张独立判断 |
| 观察期或样本不足 | 留未知，说明何时有资格判断，必要时缩小投入 |
| 使用后行为与假设相反 | 检查测量和替代解释，降低或改写相关需求/机制主张 |
| 行为改善但成本收益不合适 | 可保留需求，调整价值主张、渠道、主次或投入 |
| 多源支持且经济条件可接受 | 才讨论扩大；仍遵守预算、产能及既有权限 |

一次反证不必删整张卡，一次正向结果也不提升所有主张。每次保留原说法、新证据、适用范围、原因、受影响动作和有效版本；无变化也说明为何维持。

## 最小记录结构

现有系统能表达这些内容即可，不要求新建数据库。以下是通用逻辑字段，不是声称后台已有这些字段：

- **来源记录：** source_id、store_id、location、captured_at、business_window、time_basis、filters、schema_version、coverage、status、last_complete_window、errors。
- **证据记录：** evidence_id、source_id、row_or_locator、occurred_at、observed_at、evidence_type、claim_ids、supports_or_challenges、limitations。
- **判断记录：** claim_id、原说法、需求/约束/机制/经济类型、证据与反证、当前判断、适用范围、关键未知、改判条件、版本。
- **经营交接：** decision_id、目标及理由、保留/调整/暂缓/放弃、当前关键产出、接收岗位、关键要求、使用条件、四层验收、待核事实、资源权限、关联任务。
- **反馈记录：** event_id、实际执行、结果窗口、证据定位、原判断→新判断、动作变化、记录人/角色、保存位置与版本。

保存要核同店、当前版本和授权，防重复、错店、静默覆盖；实际写回后回读。只形成建议时明确未写回。需要共用状态时复用团队约定的当前库；共享方法包不包含真实业务记录。
