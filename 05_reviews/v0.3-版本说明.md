# v0.3：沿已有团队工作台改进

2026-09-20。v0.3 试用版，基于公开 v0.2 提交 `807c46bbf4eae64fc2db10981809f785a100afe5`，经负责人授权发布。版本入口为 [GitHub v0.3](https://github.com/clank123/blackshark-team-os/releases/tag/v0.3)。本轮未写入飞书、未发送运营群；新增真实会议和门店当前记录不属于公共发布内容。

## 方法该改什么

保留原有主干：整体方向结合本店现实，判断顾客为什么来、希望改变什么，再落到产品、表达、传播、现场承接、责任与倒排。保留既有七段式方案及推进表的协作分工。

本版重点修订 AI 怎样带人使用方法：先接住现有方向，缺口只影响对应事项；方向模糊时给有依据的候选，边讨论边成稿；日常问题直接处理，不要求先完成整套月度规划。方法、成果模板、当期事实分别更新，避免把某店本月的安排变成全店长期规则。

## 下次会有什么不同

| 使用情境 | v0.2 源码约定 | v0.3 的处理 |
|---|---|---|
| 拿到方向，但负责人或预算没齐 | 缺关键输入只交缺口 | 先形成可讨论的方案与任务树，未定内容挂在相关项 |
| 不知道本店怎么接总部方向 | 需要先提供主次方向 | AI 结合本店材料提出候选与取舍，逐步梳理 |
| 只想做两条视频或解决一次配合问题 | 主要只有月度入口 | 直接交所需稿件或安排，不启动整套月度交付 |
| 同一家店带来新会议、现场变化或结果 | 主要使用共享店卡和当月输入 | 更新本地当前记录，处理受影响的旧判断，下次按店名读取 |
| 项目中有跨板块工作 | 动作名称作为身份，十业务字段 | 保留原字段，增加稳定编号及父任务，按项目组织子任务 |
| 发布方案与表 | 主要核验表链接 | 正文、表数据、原生父子展开、真实内嵌分别核验 |

原版使用效果“一般”是负责人的反馈。上述是源码核对后找到的具体限制；没有成员全程使用记录，不能断言它们解释了所有体验问题。

## 固定且可迭代的成果

工作台、两个原名 Skill 与方法版本为 0.3；方案、表模板各为 0.2。

- 运营每月仍看一份方案、一张推进表。主项目下展开子任务，方案中内嵌实际表视图，是正式飞书成果的要求。
- 技术编号、JSON、CSV 和检查回执由 AI 维护；这些是生成与核验的材料，不增加运营的阅读作业。
- 公共包保存方法、模板及原有历史门店卡。新会议和门店当前记录放个人目录；无地图也可先工作。不会自动获取另一台电脑上的资料。
- 更新公共版本时保留个人目录、地图及本地修改；本地经验不会自行公开或升格为团队规则。

## 做过的检查

两个 Skill 的格式检查通过；22 项本地测试通过，覆盖历史证据、任务身份、父子与依赖关系、日期、缺口、状态一致性和导出。检查命令：`python3 -B -m unittest discover -s tests -v`。

独立代理按虚构输入实际完成两个场景，主代理回读了结果：

- [月度样稿](fixtures/v0.3-forward-check/scenario-a/03_my_workspace/01_projects/2030-04-河畔店/02_drafts/2030年4月河畔店月度运营方案.md)：2个主项目、10个子任务；缺人和日期仍交工作稿，正式检查拒绝未定普通任务。
- [日常样稿](fixtures/v0.3-forward-check/scenario-b/运营答复与两条视频稿.md)：无月度会议、无地图时，交两条约15秒的分镜、字幕和发布文案。

回放发现空父编号会导致预览漏项，以及“待定”负责人会通过正式检查，均已修正。复核又发现完整验收句中的“未知”被误判为缺口，已缩小为仅拒绝完整占位值；对应回归已加入。独立代理重放原输入，确认空父编号被拒绝、未定负责人被拒绝、原具体验收不再误拒。

这些结果支持本地工作稿与日常求助的可用性；不等于真实团队已经采用或负担已经下降。两个场景在同一评估代理中隔离输入执行，不是跨设备实际试用。

## 尚未证明的部分

本轮没有操作飞书，原生父子展开、方案内嵌、人员映射及权限尚未实测。模板保存目标结构，脚本只导出本地数据；它不是飞书发布器。团队后续使用时，实际能力不足要明确记录剩余步骤，不能以缩进或普通链接冒充完成。

下次收到真实材料或使用反馈，先修受影响的门店记录、方案或任务；有证据支持的共性问题再修方法、模板或 Skill。实际采用、执行收益和经营结果仍待真实证据，不另要求团队填写测试报告。
